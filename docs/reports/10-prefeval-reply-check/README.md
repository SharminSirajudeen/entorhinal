# 10: PrefEval at 300 turns, the reply check kill test (28–29 Oct 2026)

**Question.** After about 110,000 tokens of unrelated chat, does this app follow a preference the user stated at the
start, and does the reply check (checking the reply against the memory before it is sent) earn the pitch?

**Pass rule, fixed before any paid call** (commit `33df6cc`):
- ours scores at least 85%;
- ours beats RAG top-5 by at least 15 points (6 of 40).

## Result
**FAILED.** ours 24/38 (63.2%), against the 85% bar; RAG 29/38 (76.3%). Ours is 13 points below RAG, not 15 above.

| n = 38, judge Ultra | Correct | Violates the preference | Unhelpful | Mentions the preference |
|---|---|---|---|---|
| `zero`: full history | 11 (28.9%) | 27 | 0 | 2 |
| `remind`: full history + reminder (oracle) | **33 (86.8%)** | 5 | 0 | 35 |
| `rag`: full history + SimCSE top-5 | 29 (76.3%) | 8 | 1 | 30 |
| `ours_draft`: memory, the premise check + the answer step | 17 (44.7%) | 17 | 5 | 22 |
| `ours`: + the reply check | 24 (63.2%) | 11 | 9 | 27 |

`results.json` holds the verdicts per item. The counts are from `run.py`'s own tally, and a recount from the rows gave
the same numbers.

**What the reply check did:**
- It rewrote 36 of 38 drafts, so it flags far too often.
- Draft to final:

  | Draft | Final | Items |
  |---|---|---|
  | wrong | right | 11 |
  | right | wrong | 4 |
  | right | right | 13 |
  | wrong | wrong | 10 |

- Net +7, from 44.7% to 63.2%.
- All 283 findings named a fact id the memory held, so the product's stored-fact filter (PR #1) would not have
  changed this run.
- Unhelpful answers rose from 5 to 9.

**Why the memory loses the preference.** Read in 3 failing items, not counted across all 38:
1. **extraction treats every user message as a fact about the user.**
   - An inter-turn where someone writes "92 year old man with inguinal pain" became the user's health (`s23f2`).
   - the premise check and the answer step then led with it ("you're a 92-year-old man...") and violated the preference, or gave no
     recommendation.
2. **The extraction prompt change made a junk fact.** "dislikes: not specified" (`s15f10`) was extracted from an inter-turn,
   and the change judge then marked the real preference stale.
   - This change was plan step 1, measured here and in PR #1.
   - It can make false "outdated" flags anywhere. That is report 08's failure, which this run did not measure on
     STALE.

**Consequences:**
- By the rule fixed beforehand, the reply check is not the pitch.
- PR #1 (the reply check plus the extraction prompt change) passed the gate (`gate/local` success on `9f7d46c`, all 200 mutants killed).
  It is **not merged**:
  - its extraction change caused a measured junk-fact stale flag (point 2 above);
  - its effect on STALE was not measured.

## Setup (`run.py`)
**Data:**
- PrefEval explicit preferences (Zhao et al., ICLR 2025, arXiv 2502.09597).
- 2 items per topic × 20 topics = 40, seed 7.
- 300 inter-turns: PrefEval's own `filtered_inter_turns.json`, 23 conversations cut at 600 messages, as its code
  does. That is about 110,000 prompt tokens (measured: 109,968–111,091 on the dry run).

**Five answers per item:**

| Answer | What it gets |
|---|---|
| `zero` | Full history, then the question |
| `remind` | Full history, then the question with PrefEval's reminder sentence |
| `rag` | Full history, then PrefEval's stored SimCSE top-5 exchanges and the question, as its code builds it |
| `ours_draft` | The app's write path (extract, relate, judge, store; one session per conversation), then the premise check and the answer step: the app without the reply check |
| `ours` | `ours_draft`, then the reply check prototype |

- **Answer model:**
  - The baselines answer with Super, thinking on (the stronger setting).
  - Ours uses the app's own settings: the premise check Super with thinking on, the answer step Super with thinking off, the reply check Lightning, and a
    rewrite by Super with thinking off.
  - The reply to the preference statement is generated by Super, as PrefEval does with the model under test.
- **Judge:** Ultra, temperature 0, with PrefEval's own prompts read at run time.

**The the reply check prototype, in the runner:**
- Lightning lists any part of the draft that breaks a stored fact or rule (JSON).
- If any, Super rewrites the draft once with the problems named.
- extraction's prompt adds "preferences, dislikes, and standing rules about what to do or avoid". That is plan step 1.

## Deviations from the plan, each decided before results
- **Judge prompts are PrefEval's own,** read from its files at run time and never committed. The plan said
  paraphrased; the exact text matches the paper better and still keeps CC BY-NC text out of this MIT repo.
- **The hallucination check is not run.** PrefEval's accuracy rule (`get_preference_following_accuracy_generation_task.py`)
  counts every violation as wrong whatever the acknowledgement. Its accuracy is therefore "no violation and
  helpful", and the hallucination answer never changes a verdict.
- **`ours_draft` added:** the same run judged before the reply check, so the reply check's own effect is measured.
- **n = 38, not 40.** PrefEval's stored RAG file for `entertain_games` is cut off in its own repo (240,253 bytes,
  equal to the upstream `content-length`), and it does not parse.
  - The first run stopped there after 4 items.
  - The topic is skipped for all five answers. Its draw still happens, so the other topics keep their items.
  - The order is shuffled with the seed, so if the cap stops the run, the finished items are a random subset.
  - Every call is cached, so the restart paid nothing twice.
- **Price:**
  - The plan guessed ≈ $3.
  - The dry run measured $0.1437 for one item, including the one-time extraction pass over the inter-turns.
  - **Spent: $5.6407 in all**, under the $8 go. That is every live call recorded in the run's cache at list prices,
    the dry run and the stopped first run included.
- **Code:**
  - Run at `f950a73`, with this folder's `run.py`.
  - It changes extraction's prompt in memory (`S4_RULES`), so it needs `main`'s original prompt to rerun.

## Not comparable with the paper
- The paper's judge is Claude 3 Sonnet; ours is Ultra.
- The answer model differs.
- n = 40, 2 per topic; the paper's averages use every item of each topic.
